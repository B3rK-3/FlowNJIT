# Plan: New Features for FlowNJIT

## Overview

Two features:
1. **Planner Panel** — Separate flowchart section where users can add multiple classes and see them on the same plot
2. **Schedule Iteration Chat** — Generate a schedule via chat, view it, then iterate on it with a specialized AI chatbot

---

## Feature 1: Planner Panel

### Goal
A dedicated "my courses" planner panel accessible via a plus button (+) next to the chat toggle in the bottom-left corner. Users can search and add courses to this panel, which renders them on a filtered graph showing only the selected courses and their prerequisite connections.

### Frontend Changes

**File:** `website/app/components/HomeClient.tsx`
- Add state: `plannerCourses: string[]` — list of course names the user has added to the planner
- Add state: `isPlannerOpen: boolean` — controls panel visibility
- Add state: `plannerGraphData: CourseStructure` — filtered graph containing only planner courses and their prerequisite chain
- Pass `plannerCourses` and `plannerGraphData` down to `CourseGraph` when in planner mode

**File:** `website/app/components/ChatPopup.tsx` (or wherever the chat button lives)
- Move chat toggle from bottom-right to bottom-left
- Add a plus button (+) to the left of the chat toggle (bottom-left corner)
- Plus button opens the `PlannerPanel` when clicked

**New File:** `website/app/components/PlannerPanel.tsx`
- Slide-out drawer/panel (from left side) containing:
  - Search bar with autocomplete to find and add courses
  - List of added courses with remove (×) buttons
  - **The `CourseGraph` component in full graph view** rendering only the added courses + their full prerequisite chains
  - "Clear All" button to reset the planner
- Search: call existing `/chat` endpoint with `course_query` tool
- When a course is added, traverse the full course data to find all prerequisite courses (direct and transitive) — include them in the graph so users see the complete chain they need to complete
- When a course is removed, prune any prerequisite-only nodes that have no remaining children in the planner set
- Styling: dark-themed panel to differentiate from main graph, toggle button is the (+) plus icon
- Graph: renders all added courses + their prereq chains (no 40-course limit in planner mode)

**File:** `website/app/components/CourseGraph.tsx`
- Accept an optional prop `plannerMode?: boolean`
- In planner mode:
  - Don't apply the default `visibleCourses` limit of 40
  - Allow pan/zoom to navigate small graphs comfortably
  - Show a "center on these courses" button

**File:** `website/app/constants.ts`
- Add `PlannerCourseData` type for the filtered graph data structure
- Add API call helper `searchCourses(query)` for planner search

### Backend Changes (Planner Panel)

The Planner Panel is **purely frontend**. It uses data already fetched via `/getcourses` to build the prerequisite graph client-side. No backend changes required for Feature 1.

**Optional optimization (post-phase-1):**
- New endpoint `GET /courses/prereq-chain?courses=CS101,MATH111` — returns the transitive prerequisite closure for a set of courses, so the frontend doesn't have to traverse the full course graph client-side

## Feature 2: Schedule Iteration Chat

### Goal
After generating schedules via the main chat, users can select one and enter a "schedule iteration" mode where a specialized AI chatbot helps them refine the schedule: swap sections, change instructors, find alternatives, check conflicts.

### UX Flow

1. User prompts the main chatbot to generate a schedule (existing behavior)
2. User sees up to 5 schedule options in the `ScheduleViewer` modal
3. User clicks "Iterate on this schedule" button on a schedule option
4. **A new chat panel opens alongside the existing general chat** (split panel — two chat bubbles visible at once):
   - The iteration chat shows the selected schedule at the top as a compact pinned summary
   - The iteration chatbot is pre-loaded with the full schedule context
   - The general chat remains accessible and visible
5. User can say things like:
   - "Change CS 101 section 001 to section 002"
   - "Find me a Biology class without Professor Smith"
   - "Same schedule but morning classes only"
   - "What if I swap MATH 111 for a different time?"
6. The iteration chatbot responds with a modified schedule (in the same `type: "schedule"` chunk format), which updates the ScheduleViewer in-place
7. User can click "Done" to close the iteration chat panel (general chat remains)

### Frontend Changes

**File:** `website/app/components/ScheduleViewer.tsx`
- Add an "Iterate" button on each schedule card (button with a refresh/edit icon)
- When clicked, sets `isIteratingOnSchedule: true` with `currentIteratingSchedule: Schedule`
- The Iterate button passes the schedule into the chat context

**File:** `website/app/components/ChatPopup.tsx`
- Add a new `mode: "general" | "schedule-iteration"` prop (or separate ChatPopup instances)
- In `schedule-iteration` mode:
  - Display the current schedule as a pinned header/panel above the chat messages
  - Prepend system context: "You are helping the user modify their selected schedule. Available actions:..."
  - All AI responses that contain schedule modifications use `type: "schedule"` chunks (same as main chat)
  - The chat prompt includes the full schedule object at the start of the conversation
  - Show an "Exit Iteration" button to close the panel
- When in iteration mode, the chat input placeholder changes to: "Ask to change a section, swap a professor, adjust times..."
- **Split panel layout:** Position the iteration chat below or beside the general chat. The general chat stays open and visible.

**File:** `website/app/components/HomeClient.tsx`
- Add state: `currentIteratingSchedule: Schedule | null`
- Add state: `isIteratingOnSchedule: boolean`
- When `isIteratingOnSchedule` is true, pass the schedule to ChatPopup
- The ScheduleViewer update flow remains the same (chat responds with new schedule chunks)

**File:** `website/app/constants.ts`
- Add `Schedule` type to match the `make_schedule` return format:
  ```typescript
  interface Schedule {
    sections: Section[];
    days_used: string[];
    num_days: number;
  }
  interface Section {
    course: string;
    section_id: string;
    days: string;
    crn: string;
    times: string;
    location: string;
    instructor: string;
    parsed_times?: Record<string, [number, number][]>;
  }
  ```

### Backend Changes

**New Endpoint:** `POST /schedule-chat`

**File:** `backend/server.py`
- New endpoint that accepts a schedule + message + term
- Streams responses in NDJSON (same format as `/chat`)
- Uses the same Gemini streaming infrastructure but with a different system prompt

**File:** `backend/functions.py`

**Planner Panel tools** (Feature 1 — prerequisite eligibility check):

**A. `check_planner_conflicts(course, session_id)`**
- Input: course name, user's session ID (to look up their profile)
- Behavior:
  - Load the user's `UserFulfilled` profile from Redis (`session_id:prereqs`)
  - Run `check_prereq_tree` on the course against the user's completed courses
  - Returns: `{ "conflicts": true/false, "conflict_details": [...] }` where conflict_details lists missing prerequisites or other unmet conditions (e.g., standing requirement)
- Used by the Planner Panel to **block courses the user cannot currently take** (missing prereqs, standing requirement, permission needed) before adding to the graph
- Note: The Planner Panel shows courses on a prerequisite graph — it does NOT deal with section times or schedule conflicts. `check_planner_conflicts` validates prerequisite eligibility only.

**Schedule Iteration Chat tools** (Feature 2):

**1. `change_section(schedule, course, new_section_id)`**
- Input: current schedule object, course name (e.g. "CS 101"), new section ID (e.g. "002")
- Behavior:
  - Find the new section data from `COURSE_DATA[course].sections[term]`
  - Validate the new section has no time conflicts with other sections in the schedule
  - Validate the new section satisfies any user constraints (honors, RMP rating, day preferences)
  - Return: `{ "schedule": <new_schedule_object>, "changes": "Changed CS 101 from section 001 to 002" }` or error
- Time conflict check uses existing `has_time_conflict()` logic

**2. `find_alternative_section(schedule, course, exclude_instructor?, preferred_days?, earliest_time?, latest_time?)`**
- Input: current schedule object, course name, optional filters
- Behavior:
  - Get all sections for the course from `COURSE_DATA[course].sections[term]`
  - Filter out the currently selected section
  - Apply the optional filters (instructor, days, time)
  - Check time conflicts against remaining sections in the schedule
  - Return: list of alternatives with their times/instructor/conflict status, or error if none found

**3. `check_schedule_conflicts(schedule)`**
- Input: schedule object
- Returns: list of any time conflicts within the schedule (overlapping sections on same day/time)
- Used in iteration chat for diagnostics ("does my schedule have any conflicts?") and implicitly validates every change via `change_section` / `reschedule_course`

**4. `reschedule_course(schedule, course, preferred_days?, earliest_time?, latest_time?, min_rmp_rating?)`**
- Input: current schedule, course name, new preferences
- Behavior:
  - Clear the section selection for that course
  - Re-run the filtering logic from `make_schedule` for just that one course
  - Find sections that fit with the rest of the schedule (no conflicts)
  - Return the best alternatives

**New System Prompt for `/schedule-chat`:**
```
You are a schedule optimization assistant. The user has generated a schedule and wants to modify it.
You have access to tools to change sections, find alternatives, and reschedule courses.

Current schedule:
{sections: [...], days_used: ["M","W","F"], num_days: 3}

User constraints to respect:
- If user asks to "change this section" → use change_section
- If user asks to "find me a class without Professor X" or "find me a morning section" → use find_alternative_section
- If user asks to "reschedule MATH 111" or "find me a different time for X" → use reschedule_course
- Always confirm changes before reporting success
- When returning a modified schedule, use the same format the user expects

Respond conversationally. For schedule changes, end by asking "Any other changes?"
```

**File:** `backend/types.py`
- Add `ScheduleChangeRequest` type for the `/schedule-chat` request body
- Add `SectionReplacement` / `AlternativeSection` response types
- Add `ScheduleModificationResult` type

### Request/Response Format for `/schedule-chat`

**Request:**
```json
{
  "message": "Change CS 101 to section 002",
  "term": "202610",
  "schedule": {
    "sections": [...],
    "days_used": ["M", "W"],
    "num_days": 2
  },
  "user_constraints": {
    "min_rmp_rating": 0,
    "honors": false,
    "earliest_time": null,
    "latest_time": null
  }
}
```

**Response:** Same NDJSON streaming format as `/chat`:
- `{"type": "text", "content": "Changing CS 101 from section 001 to 002..."}`
- `{"type": "schedule", "content": {"sections": [...], "days_used": ["M", "W"], "num_days": 2}}`

### State Management

- The `schedule` is passed with every request to `/schedule-chat` (no server-side session needed for iteration)
- The frontend tracks `currentIteratingSchedule` and updates it when a new `type: "schedule"` chunk arrives
- On "Exit Iteration", the final state of the schedule is stored in the regular chat session history so it's not lost

## Implementation Order

### Phase 1: Planner Panel (Feature 1)
1. Add `plannerCourses`, `isPlannerOpen`, `plannerGraphData` state to `HomeClient.tsx`
2. Create `PlannerPanel.tsx` with search + course list

1. Add `Schedule` type definitions to frontend

3. Implement schedule iteration tools (`change_section`, `find_alternative_section`, `check_schedule_conflicts`, `reschedule_course`)
4. Wire up split panel: add second `ChatPopup` instance for iteration alongside existing general chat
5. Add "Iterate" button to `ScheduleViewer.tsx`
6. Test end-to-end: generate → iterate → modify → view updated schedule

### Phase 3: Polish & Edge Cases
1. Handle "no alternatives found" gracefully in iteration chat
2. Add loading states during section lookup in iteration chat
3. Ensure ScheduleViewer updates correctly during iteration
4. Dark mode styling for PlannerPanel
5. Smooth panel open/close transitions for both panels
